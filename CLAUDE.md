# Social Ops: in-house social media system

## What this is
An internal tool for our agency (Chania, Crete) to plan, create, approve and organize social media posts for **many client accounts**, faster.

**Organize mode (since 2026-11-04, D16):** the app organizes the work; the team posts in the apps by hand. Everything that posts through our drivers or reads back from the platform APIs (accounts and OAuth, publish queue, token monitor, preflight, reconcile, Withdraw, comment inbox, insights, monthly numbers, listening report) stays in the code but is off behind `FEATURE_PUBLISHING` (`config/features.php`, routes under `feature:publishing`, the scheduler, `@if (config('features.publishing'))` in the views). Tests run with the flag on (`phpunit.xml`) plus `OrganizeModeTest` for the off state. The sections below still describe the publishing features; read them as "when the flag is on". Clients are mostly hospitality: villas, hotels, beach bars/lounges, restaurants, local brands. Content is **Greek and English**.

Goal: cut time from every step: asset intake, captions, translation, approvals, scheduling, reporting.

## Core idea
Own the workflow and the publishing. No paid middleman.
- We build: client/brand profiles, asset inbox, content calendar, AI bilingual captions, client approval portal, reporting.
- We build the publishing too: our own Meta developer app (Instagram + Facebook via the Graph API), TikTok Content Posting API, each a driver behind a `Publisher` adapter interface (LinkedIn, added 2026-11-04 with D17, has no driver: planned and approved here, posted by hand). No paid aggregator (Panos's call, D2).
- Consequence: platform approvals (Meta App Review, TikTok audit) are the critical path. Start Phase 0 today. Build and test every driver in dev mode with the agency's own test accounts while approvals run; client publishing goes live per platform as each approval lands.

## MVP scope (Phase 1)
1. Client & brand profiles (accounts, voice, languages, pillars, hashtag bank, approval policy, approver contacts).
2. Asset inbox per client: no-login upload link, auto-naming, tags.
3. Content calendar with post state machine.
4. AI drafting: Claude API, EL + EN captions, per-platform variants, alt text, hashtags.
5. Client approval portal: signed expiring magic links, per-network previews, inline comments, approve on mobile, reminders. A client without approvers in the profile still gets the review and its link (no e-mail; the Approvals page says to send the link by hand). Every approval mail (request, reminder, overdue, "all answered") goes through `App\Mail\Outbox::send()`, which logs a mail server problem instead of throwing: the client's answer and the hourly `reviews:remind` never fail because of mail.
6. Publishing to Instagram, Facebook and TikTok through our own drivers; LinkedIn by hand. TikTok posts stay private (SELF_ONLY) until the audit passes; until then public TikTok posts go through Manual-Needed. No other platforms, now or later.
7. Token health monitor, plus `posts:preflight` (hourly: every account with a post due in the next 24 hours answers one cheap API call, or Slack hears about it once a day).

Out of MVP: CSV import, evergreen queues, Canva autofill, auto-reports, auto-Reels. LinkedIn, YouTube, Threads, Pinterest and X are not planned.

## Post state machine
`Idea → Draft → In Review → Changes Requested → Approved (locked) → Scheduled → Published | Failed | Manual-Needed`, and `Published → Withdrawn` (the Withdraw button deletes the post through the Facebook API; Instagram and TikTok have none, so those stay listed on the post with a note until a human deletes them in the app).
- Approved posts are locked; editing one sends it back to In Review.
- Approval auto-schedules the post.
- A post with `settings.repeat` (weekly or monthly) spawns its next occurrence as a Draft right after it is published (`Post::spawnRepeat()`); the Draft goes through approval again.
- Code: `App\Posts\PostState` (enum with the transitions, `color()` for the badge classes; every page shows a state through `<x-state-badge :state>`, the calendar legend filters by state), `Post::transitionTo()`; captions live in `post_variants` per platform and language; `Post::captionFor()` builds the published text (languages, then the profile's `signatures.<platform>` line, then the hashtags).
- Numbers: `posts:insights` (daily) reads reach, views, likes, comments, shares and saves per platform into `posts.metrics` from Instagram, Facebook and TikTok (Display API, scope `video.list`).
- Manual-Needed covers things no API can do (Instagram Story stickers, shopping tags, public TikTok through our own app before its audit): notify a human to post in-app.

## Rules that must not be broken
- Never store client passwords. Official OAuth only.
- Never hard-code platform quotas. Read live limits (for example Instagram `content_publishing_limit`) before batch publishing.
- A human stays in the approval gate. AI drafts; it never publishes unapproved content.
- Greek captions get human review (gender agreement, idioms).
- Client data and media in EU-region storage. Log UGC repost permission and consent for people in assets.
- Each client is isolated: accounts, media, users, data.

## Dev setup
`composer install && cp .env.example .env && php artisan key:generate && php artisan migrate && npm install && npm run build`. The first staff login is created on `/setup` (only while there are no users) or with `php artisan staff:create "Name" email`; more logins on the Staff page (no public registration). A login can be limited to some clients there (`users.client_ids`, enforced by `App\Http\Middleware\LimitClients` on every staff page and in the lists): it sees only those clients and cannot manage logins. Run `php artisan test` and `vendor/bin/pint --test` before every commit; CI runs both. On the server, `/refresh` (the "Refresh after update" page, linked in the side navigation for admins, admins only since 2026-11-06) runs the migrations and `optimize` after a pull. Reminders and escalations need the scheduler (`php artisan schedule:work` locally, cron in production).

## Conventions

Long forms are sections (`<x-section title description>`, one per tab of a side list, Alpine `tab`) of rows (`<x-field label for help>`: label and help on the left, the control on the right). `public/build` is committed (no Node on the server): run `npm run build` before committing a view change that adds Tailwind classes. Contrast and plain words (2026-11-06, "dumb down the UI and add more contrast"): no `text-gray-400` or lighter for text on light surfaces (secondary text is `text-gray-600`, faint `text-gray-500`), card borders `border-gray-300`, form fields get a 3:1 border from `app.css`; the side navigation is dark in both themes, so it uses the `neutral` greys, which the dark remap leaves alone; dark mode is the remap block in `app.css` (the state badges included), so a new light class that needs a dark look goes there; help texts say what a thing is for in one short sentence; the post page shows the usual next step (`PostState::forward()`) as the orange button; the calendar keeps the date range, platform and pillar behind "More filters".
- Admins (`users.is_admin`: Panos's login by the migration, else the oldest login; the first login made on `/setup`; the Admin tick on the Staff page, admins only) get the Settings page (`/settings`, `SettingsController`, Gate `admin`): every variable of `.env` edited in the browser, written back in place (comments kept, the previous file as `.env.backup`), then `config:cache`; `APP_KEY` is locked. "Send a test e-mail" at the top of the page mails the admin with the current mail settings and shows the mail server's own error when it fails.
- Asset/post naming: `CLIENT_YYYYMMDD_PLATFORM_FORMAT_PILLAR_LANG_v#`, e.g. `ALMYRA_20270512_IG_REEL_FOOD_EL-EN_v2`. Enforced automatically on upload (the version is the highest in use + 1 and never a file already on the disk, so a deleted file cannot make an upload overwrite another); raw inbox uploads use `ANY` for the platform and `IMG`/`VID` for the format (e.g. `ALMYRA_20261103_ANY_IMG_FOOD_EL-EN_v1.jpg`) because platform and post format are decided later on the post.
- Assets page (`/clients/{id}/assets`, `AssetController`, rework of 2026-11-06, Panos: "the staff could be able to upload photos for each project"): "Add files" comes first with the team's own upload: drop photos and videos anywhere on the page or pick many, one pillar, season, note and the consent ticks for the batch (`POST /clients/{id}/assets`, `AssetController::store()`, staff only and behind `LimitClients`). The page sends one file per request, three at a time, each with its own progress line, and reloads when all went in; a plain form post sends them all. Every file is checked on its own against the client link's rules (`InboxUploadRequest::fileRules()`, `MIMES`, `MAX_KB`) and filed through `Client::storeAsset()` with `uploaded_via` staff, so a refused or failed file never stops the others (JSON answers `uploaded` and `failed`, 422 when nothing went in). Under it, "Other ways to add files" is folded: the client's upload link with Copy, Google Drive, Dropbox and Canva, open while one of them is being set up. "Tools" folds the Reel maker, which lists the clips in the order they play. The files grid filters by a search (name, file name, season, note, pillar as shown), photo or video, pillar, and used in a post or not (a post in the recycle bin still uses its file; `AssetController::FILTERS`, kept through a delete). Each file opens a preview (`/assets/{id}/view`, `Asset::inline()`), downloads, or deletes after a confirm that names the posts, binned ones too, that would lose it. `Asset::sources()` lists every `uploaded_via` value with its label (link, staff, drive, dropbox, canva, reel).
- Clients board (`/clients`): one row per client with the agency's own fields from the profile's Agency tab (`clients.status`, `owner`, `priority`, `plan_due`, `posts_per_week`, `stories_per_week`, `tiktoks_per_month`, `pending`, `links`; `Client::STATUSES`, `Client::PRIORITIES`), the date the calendar is scheduled up to, this week's and the waiting-for-client counts; soonest plan due first, overdue in red. The Approved and Scheduled posts (Manual needed too while posting is on) due today across the login's clients, plus the last 7 days' ones nobody marked published (flagged late), soonest first, a client filter and a Today / Tomorrow switch. Per post the media (thumbnails, Download, the ZIP) and per ticked platform the text to paste: `Post::pasteText()` (what `captionFor()` publishes, without its checks, which show as a red line instead), each language alone when there are several, the first comment (`Post::firstCommentFor()`) and the alt text, each with a Copy button (`<x-copy-button>`, "Copied" until the page reloads). - The Claude queue in sight (`App\Planning\ClaudeQueue`): the plan requests (`claude_job` reports, the request in `meta`) and the caption requests (`settings.ask_claude`; `Post`'s saving hook keeps the tick's time in `settings.ask_claude_at` and drops it with the tick) are listed in the MCP-mode "Plan with Claude" box (that client's plans, with Cancel, `claude.cancel`) and under "Waiting for Claude" on the Jobs page (the login's clients, Cancel and "Stop asking", `claude.stop`, which unticks without sending an approved post back to review).
